# Release metadata

> **Audience:** Release owners, GitOps reviewers, and security reviewers
> **Outcome:** Determine whether one immutable release subject carries the evidence, compatibility,
> migration, and rollback lineage required for selection, promotion, and production admission.

## Authority and schema

Release records are generated by `mindclade-internal-monorepo` and enter this repository only
through reviewed promotion pull requests. Each `releases/**/*.json` record conforms to contract
`4.0.0` in
[`contracts/release-metadata.schema.json`](../contracts/release-metadata.schema.json).

A record binds one content-addressed subject to:

- its release kind, full source commit, builder identity, and invocation;
- one or more logically named immutable images;
- typed content-addressed artifacts, including SBOM, provenance, vulnerability, qualification,
  and rollback records;
- a subject-bound evidence graph, exact policy digest, and qualification epoch;
- distinct ARC build/provenance, qualification, and protected deployment attestors, each bound
  to the immutable reusable-workflow release that exercised its signing authority;
- explicit Kubernetes/platform compatibility and required capabilities; and
- migration intent plus an exact previous release ID and subject digest for rollback, or an
  explicit bootstrap strategy when no previous release exists.

Image and artifact names are stable logical keys inside the record. Environment deployment files
select only the record; they may not restate or override any image, artifact, or evidence field.
Runtime manifests may consume a typed artifact through the explicit tokens documented in
[`deployments/README.md`](../deployments/README.md).

GitOps owns selection and validation, not evidence creation. The dedicated deployment signer
can issue the runtime trust root only after verifying the independent build and qualification
occurrences; GitOps cannot create any of those attestations.

## Validate

```sh
python3 scripts/validate-release-metadata.py
python3 scripts/validate-deployment-selections.py
```

`provenance.yml` runs trusted v2 selection validation against the candidate checkout, enumerates
the named images from the selected records, validates every record, and then verifies the external
deployment attestation. A missing, mismatched, mutable, or unverifiable field is a release failure;
do not edit evidence to make validation pass.

See [artifact deployment selections](../deployments/README.md),
[workload activation](../docs/workload-activation.md), and
[Binary Authorization recovery](https://github.com/mindclade/infrastructure-live/blob/main/docs/runbooks/binauthz-blocked-deploy.md).
